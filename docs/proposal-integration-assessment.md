# Foundation 3J – Proposal Integration Assessment

## Scope

This is a report-only assessment for integrating Nail Shop proposal drafts, pricing, policies, and the Full Set Renderer into the proposal system later. It intentionally does not change runtime app code, proposal behavior, routes, blueprint logic, cost-engine logic, or Design Studio files.

## 1. Current Proposal System

### Current proposal data model

The persisted v1 proposal model is intentionally small and design-linked:

| Field | Source / behavior | Notes |
| --- | --- | --- |
| `id` | Generated by the backend on create | UUID string. |
| `designId` | Required create input | Must match an existing design before a proposal can be created. |
| `clientName` | Required create input | Trimmed before persistence. |
| `price` | Required create input | Parsed as a number; backend requires it to be positive. |
| `status` | Backend assigned at create | Initial status is `Sent`. |
| `notes` | Optional create input | Also reused for client change-request notes when status changes. |
| `createdAt` | Backend assigned at create | Millisecond timestamp in app store shape; SQL column is `created_at`. |
| `design` | Embedded response data | Populated when listing/fetching proposals; not a proposal-owned snapshot. |
| `blueprintSummary` | Embedded response data when available | Derived from the linked design/blueprint at read time. |

The SQL schema stores the same core fields as `id`, `design_id`, `client_name`, `price`, `status`, `notes`, and `created_at`. Proposal status history is stored separately with `proposal_id`, `old_status`, `new_status`, `note`, and `created_at`.

### Current create flow

1. `Proposals.jsx` loads proposals and designs together.
2. The create form asks for design, client name, price, and optional notes.
3. The frontend validates that a design is selected, client name is present, and price is a non-negative number.
4. The frontend posts `{ designId, clientName, price, notes }` to `POST /api/proposals`.
5. The backend validates `designId`, verifies the design exists, validates `clientName`, requires `price > 0`, assigns `status: "Sent"`, assigns `createdAt`, persists the proposal, writes an initial status-history entry, and returns the populated proposal.
6. The frontend clears the form, hides it, and reloads proposals/designs.

### Current list view behavior

The internal proposal list:

- Fetches `GET /api/proposals` and `GET /api/designs` in parallel.
- Shows a loading state, error state, empty state, or card list.
- Displays design name, shape, client name, optional proposal notes, optional blueprint marketing tags, formatted price, status badge, and an “Open client view” link.
- Builds the client URL as the backend origin in local React dev ports and as the current origin otherwise.
- Does not display client contact, selected service, deposit, estimated time, policy text, draft text, or Full Set Renderer output.

### Current status behavior

Valid statuses are:

- `Sent`
- `Viewed`
- `Accepted`
- `ChangesRequested`
- `Declined`

Status transitions currently happen in three places:

- Proposal creation starts at `Sent`.
- Opening `/proposal/:id` advances `Sent` to `Viewed`.
- Client actions on `/proposal/:id/action` map `accept`, `changes`, and `decline` to terminal or response statuses.

Terminal statuses are protected: once a proposal is `Accepted`, `ChangesRequested`, or `Declined`, conflicting later status actions are rejected. Internal `PATCH /api/proposals/:id/status` can set any valid status, but store-level terminal-status protections still apply when changing from a terminal status to a different status.

### Current API/backend behavior

Current proposal endpoints:

| Endpoint | Behavior |
| --- | --- |
| `GET /api/proposals` | Lists proposals newest first with embedded design data. |
| `GET /api/proposals/:id` | Fetches one proposal with embedded design data. |
| `POST /api/proposals` | Creates a design-linked proposal. |
| `PATCH /api/proposals/:id/status` | Internal status override to a valid proposal status. |
| `GET /api/proposals/:id/history` | Lists status history oldest first. |
| `GET /proposal/:id` | Renders standalone client HTML and marks `Sent` as `Viewed`. |
| `POST /proposal/:id/action` | Records client accept/change/decline action. |

The backend supports both Postgres-backed persistence and JSON-file persistence. Both stores create proposal records with the same v1 shape and write proposal status history.

### Current limitations

- Proposals depend on a live linked design instead of proposal-owned snapshots.
- No v2 compatibility envelope or version marker exists.
- No shop snapshot exists.
- No service snapshot exists.
- No price snapshot beyond flat `price` exists.
- No deposit amount or deposit rules are persisted.
- No cancellation policy, appointment rules, press-on rules, business hours, or booking requirements are persisted.
- No client contact field exists.
- `notes` is overloaded for initial proposal notes and later change-request notes.
- No draft text is stored.
- No source field identifies whether a proposal came from manual entry, Nail Shop draft, future blueprint flow, or another origin.
- Public proposal HTML is backend-rendered and separate from React renderer components.
- The list view has no Full Set Renderer preview or hero snapshot.
- Existing proposals may fail to preserve historical business terms if the linked design or shop settings change later.

## 2. Nail Shop Data Available

Nail Shop already contains local, proposal-relevant data and helper behavior, but it is intentionally not wired into proposal persistence.

### Shop profile

Available profile fields include:

- `shopName`
- `tagline`
- `about`
- `contactEmail`
- `phone`
- `location`
- `instagram`
- `tiktok`
- `website`
- `bookingLink`
- `primaryColor`
- `accentColor`

The profile is normalized and saved in browser local storage under the Nail Shop profile storage key.

### Service menu

Available service data includes:

- `id`
- `name`
- `description`
- `category`
- `startingPrice`
- `estimatedTime`
- `active`

Default services include Classic Full Set, Fill-In, and Custom Press-On Set. Services are normalized and persisted in browser local storage.

### Pricing library

The pricing library includes reusable categories:

- Length pricing
- Finish pricing
- Nail art pricing
- Embellishment pricing
- Time add-ons
- Suggested deposit percent

Rows include `id`, `name`, and `amount`, with category-level labels and units. The pricing library is normalized and persisted in browser local storage.

### Cost engine calculation

The cost engine derives:

- selected service
- line-item breakdown
- suggested price
- suggested deposit
- estimated time
- deposit percent

Inputs include service, length, finish, art level, and embellishment counts.

### Policies and booking rules

Available policy data includes:

- Deposit rules: deposit percent, minimum deposit amount, full-payment-required flag.
- Cancellation policy: cancellation window or custom text.
- Appointment rules: grace period, max reschedules, no-show fee.
- Press-on rules: processing time, rush fee, pickup availability, shipping availability.
- Business hours by weekday.
- Booking requirements: deposit, consultation, sizing, and approval requirements.

### Proposal readiness

Nail Shop already evaluates internal proposal readiness across:

- business profile
- service menu
- pricing library
- cost engine
- policies

This readiness check is intentionally internal-only and does not create proposals, send anything externally, connect to Proposals, connect to Design Studio, or connect to Blueprint.

### Proposal draft generator

The draft generator is local-only. It can collect or derive:

- client name
- client contact
- proposal title
- proposal notes / what is included
- service type
- proposed date / turnaround
- custom message
- shop name
- business contact
- selected service
- suggested price
- suggested deposit
- estimated time
- deposit policy
- cancellation policy
- booking requirements

Generated text explicitly says it is internal and is not sent, saved, or converted to a proposal record.

### Full Set Renderer

Nail Shop imports `FullSetRenderer` for sandbox previews. It currently renders a reusable sample set in:

- Full Set Renderer preview mode.
- Proposal Draft full set hero preview.

The renderer is not connected to proposals, blueprints, storefront products, gallery, or Design Studio state in the current Nail Shop flow.

## 3. Gap Analysis

| Future need | Current proposal support | Gap / recommendation |
| --- | --- | --- |
| Full set hero preview | Not persisted or shown in proposal list/client view | Add a visual snapshot containing renderer-safe full-set data and hero metadata. |
| Selected service | Only linked design exists | Add service snapshot with service id/name/category/description/time at proposal creation. |
| Suggested price | Flat `price` exists | Keep `price` for compatibility; add price snapshot with suggested/final price and breakdown. |
| Suggested deposit | Not persisted | Add deposit amount, percent, minimum, and full-payment flag to price/policy snapshots. |
| Estimated time | Not persisted | Add estimated time to service or price snapshot. |
| Deposit policy | Not persisted | Add policy snapshot text plus structured deposit rules. |
| Cancellation policy | Not persisted | Add policy snapshot text plus structured cancellation settings. |
| Booking requirements | Not persisted | Add structured booking requirements and human-readable summary. |
| Client contact | Not persisted | Add client snapshot with name plus contact fields. |
| Proposal notes | Existing `notes` only | Keep v1 `notes`; add v2 `proposalNotes` or `draft.notes` to avoid overloading status-action notes. |
| Draft text | Not persisted | Add draft snapshot with title, body text, custom message, and generated-at timestamp. |
| Proposal source | Not persisted | Add `source` object, e.g. `manual-v1`, `nail-shop-draft`, `design-studio`, `blueprint-future`. |
| Shop branding | Not persisted | Add shop snapshot at creation. |
| Historical stability | Uses live linked design data | Snapshot all client-facing service, price, policy, shop, and visual data at proposal creation. |
| Backward compatibility | v1 proposals exist | Make v2 optional/additive and preserve v1 render/list fallbacks. |

### Compatibility notes

- Keep top-level `designId`, `clientName`, `price`, `status`, `notes`, and `createdAt` while v1 views exist.
- Add v2 fields as nullable/additive data first.
- Treat `schemaVersion` missing as v1.
- Let old proposal cards render from v1 fields exactly as they do today.
- Let new proposal cards prefer snapshots but fall back to v1 fields.
- Do not read live Nail Shop local-storage settings when rendering old proposals.

## 5. Recommended Integration Plan

### 3K Proposal Data Model v2

- Add an additive v2 storage envelope without removing v1 fields.
- Add database migration or JSON-store-compatible field for snapshots.
- Add backend validation for optional v2 snapshot payload.
- Add read fallbacks so v1 records still serialize exactly enough for current UI.
- Add tests proving old v1 proposal records still render and status updates still work.

### 3L Proposal Create Form Upgrade

- Upgrade `Proposals.jsx` in tiny steps.
- Add client contact and service selection only after v2 backend compatibility exists.
- Keep design selection optional or unchanged until product decisions are clear.
- Prefer creating v2 snapshots at submit time instead of referencing Nail Shop live settings from rendered proposals.
- Avoid importing Design Studio or blueprint logic.

### 3M Proposal Full Set Hero Preview

- Import `FullSetRenderer` only in proposal surfaces that actually render the visual snapshot.
- Store renderer-safe snapshot data with the proposal.
- Add safe fallback when visual data is missing, invalid, or from a v1 proposal.
- Do not connect proposal rendering directly to Design Studio state.

### 3N Client Proposal View Upgrade

- Migrate the standalone client proposal HTML carefully, or introduce a dedicated client-rendering path with strong fallback behavior.
- Preserve `/proposal/:id` URLs.
- Preserve `Sent` to `Viewed` behavior.
- Preserve accept/change/decline actions and terminal-status conflict handling.
- Add snapshot-based shop, service, price, policy, draft, and visual sections incrementally.

### 3O Proposal Status + Actions Hardening

- Separate proposal notes from action/history notes.
- Ensure repeated terminal client actions keep returning conflicts.
- Add explicit updated timestamps for status changes.
- Add tests for client action edge cases, missing v2 fields, and old records.
- Consider a future status-action audit model separate from mutable proposal fields.

## 6. Risk Notes

- Avoid breaking existing proposals; v1 records must continue to list, fetch, render, and accept actions.
- Keep old proposal records compatible by treating missing `schemaVersion` and missing snapshot objects as expected.
- Do not introduce a Design Studio dependency for proposals.
- Do not introduce a Blueprint dependency yet; use a future visual snapshot boundary instead.
- `FullSetRenderer` should be imported only where needed, never globally into routing or unrelated pages.
- `Proposals.jsx` should be changed in tiny steps because it currently owns fetching, create form state, validation, submission, list rendering, and client URL construction in one component.
- Be careful with `notes`: current backend status updates can replace proposal notes with client change-request notes.
- Do not let proposal render output depend on current Nail Shop local storage; snapshots should freeze proposal terms at creation.
- Backend-rendered client HTML cannot directly use React components without a deliberate rendering strategy.

## 7. Test Plan For Future Integration

Future proposal integration should include tests/checks that prove:

- Old proposals still render in internal list, API detail, public client view, and status history.
- New proposals include a v2 snapshot with client, shop, service, price, policy, visual, draft, status, and timestamps.
- Full set preview renders when a visual snapshot exists.
- Missing or invalid snapshot data falls back safely.
- Client actions still update status.
- Repeated terminal client actions still return conflicts.
- Design Studio remains unchanged.
- Nail Shop remains unchanged unless a milestone explicitly touches it.
- Blueprint logic remains unchanged unless a future milestone explicitly introduces a snapshot adapter.
- Cost engine logic remains unchanged unless a future milestone explicitly exports or serverizes pricing calculations.
- `GET /proposal/:id` preserves existing URLs and `Sent` to `Viewed` transition.
- `GET /api/proposals`, `GET /api/proposals/:id`, `POST /api/proposals`, `PATCH /api/proposals/:id/status`, and `GET /api/proposals/:id/history` remain backward compatible.

## Safe-to-merge assessment

This report-only PR is safe to merge if tests pass and the diff remains limited to this document. It creates no feature integration, no UI changes, no backend behavior changes, and no proposal behavior changes.
